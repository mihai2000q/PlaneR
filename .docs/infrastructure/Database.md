## Naming Convention

### Tables

Tables are named in **snake_case**, in the **plural** form.

Examples:

- `users`
- `calendars`
- `events`
- `event_preparation_steps`
- `tasks`
- `task_completions`
- `recurrence_exceptions`
- `refresh_tokens`
- `one_time_tokens`

**Why snake_case and plural?**

- PostgreSQL itself folds unquoted identifiers to lowercase, so snake_case avoids the need to double-quote every table
  name in raw SQL.
- Plural is the convention used by most Postgres tooling and by Flyway-generated schemas, and it reads naturally in join
  clauses (`SELECT * FROM users u JOIN calendars c ON ...`).

### Columns

Columns are also **snake_case**, in the **singular** form.

Examples:

- `id`
- `user_id`
- `calendar_id`
- `created_at`
- `updated_at`
- `scheduled_for`
- `scheduled_start_at`

**Foreign keys** follow the pattern `<referenced_table_singular>_id`. For example, a foreign key to `users` is named
`user_id`, and a foreign key to `calendars` is named `calendar_id`.

**Timestamps** end in `_at` (`created_at`, `updated_at`, `completed_at`, `starts_at`, `ends_at`). They are stored as
`timestamptz`, which Postgres keeps in UTC. **Dates** (without a time component) are stored as `date`. They end in `_on`
or `_for` when it reads well (`scheduled_for`, `occurrence_date`), otherwise they keep a name that clearly denotes a
date.

### Indexes and Constraints

- **Primary keys** are named `pk_<table>`, e.g., `pk_users`.
- **Foreign keys** are named `fk_<table>__<referenced_table>`, e.g., `fk_events__calendars`.
- **Unique constraints** are named `uq_<table>__<column>`, e.g., `uq_users__email`.
- **Indexes** are named `ix_<table>__<column>`, e.g., `ix_tasks__scheduled_for`.

Postgres-generated names for primary keys and unique constraints are acceptable if they are clear, but explicitly named
constraints are preferred for consistency.

## Schema

### Conventions

- **`id`** is a `uuid` primary key. UUID v7 values are **generated by the application**, not by a database default, so
  the id is known before the insert and ordering by creation time is preserved.
- **Ownership.** Every user-owned table has `user_id`, and every query filters by it.
- **Hard deletes.** There are no soft-delete columns. Deleted rows are gone.
- **Case-insensitive uniqueness** (emails, calendar names) is enforced with a unique index on `lower(<column>)`.

### Tables Overview

| Table                     | Purpose                                      | Notable columns and constraints                                                                                                                                                                                |
|---------------------------|----------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `users`                   | Accounts                                     | `email` (unique on `lower(email)`), `email_verified`, `pending_email`, `password_hash`, `display_name`, `avatar_url`, `timezone`                                                                               |
| `calendars`               | Groupings                                    | `user_id`, `name`, `color`, `icon`, `position`, `is_default`. Unique on `(user_id, lower(name))`. A partial unique index on `(user_id)` where `is_default` guarantees exactly one default                      |
| `events`                  | Events                                       | `user_id`, `calendar_id` (nullable), `title`, `description`, `location`, `starts_at`, `ends_at`, `time_zone`, `all_day`, `recurrence_*` columns. Check: `ends_at > starts_at`                                  |
| `event_preparation_steps` | An event's routine                           | `event_id`, `name`, `duration`, `position`                                                                                                                                                                     |
| `tasks`                   | Tasks                                        | `user_id`, `calendar_id` (nullable), `title`, `description`, `due_at`, `scheduled_for`, `scheduled_start_at`, `scheduled_end_at`, `time_zone`, `completed`, `completed_at`, `position`, `recurrence_*` columns |
| `task_completions`        | Per-occurrence completion of recurring tasks | `task_id`, `occurrence_date`, `completed_at`. Primary key `(task_id, occurrence_date)`                                                                                                                         |
| `recurrence_exceptions`   | Overrides and skips of single occurrences    | `event_id` **or** `task_id` (a check enforces exactly one), `occurrence_date`, `skipped`, nullable override columns. Unique on `(event_id, occurrence_date)` and on `(task_id, occurrence_date)`               |
| `refresh_tokens`          | Issued refresh tokens                        | `user_id`, `family_id`, `token_hash` (unique, SHA-256), `created_at`, `expires_at`, `revoked_at`, `replaced_by`                                                                                                |
| `one_time_tokens`         | Email verification and password reset        | `user_id`, `purpose`, `token_hash` (unique, SHA-256), `email`, `created_at`, `expires_at`, `used_at`                                                                                                           |

Tokens are stored **only as hashes**; the raw values exist only in the emailed link or the client.
See [Security](../security/Security.md).

### Deletion Behaviour

| Foreign key                                             | On delete  | Why                                                                                                                                                                                                           |
|---------------------------------------------------------|------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| any `user_id` → `users`                                 | `CASCADE`  | Deleting an account removes everything it owns                                                                                                                                                                |
| `events.calendar_id`, `tasks.calendar_id` → `calendars` | `SET NULL` | Safety net matching the default "unassign" mode. The **reassign** and **cascade** modes of calendar deletion are carried out by the application, inside one transaction, *before* the calendar row is deleted |
| `event_preparation_steps.event_id` → `events`           | `CASCADE`  | Steps live and die with their event                                                                                                                                                                           |
| `task_completions.task_id` → `tasks`                    | `CASCADE`  |                                                                                                                                                                                                               |
| `recurrence_exceptions.event_id` / `task_id`            | `CASCADE`  |                                                                                                                                                                                                               |
| `refresh_tokens.replaced_by` → `refresh_tokens`         | `SET NULL` | Cleanup of old rows must not be blocked by the chain                                                                                                                                                          |

### Preparation Steps Storage

An event's **routine** — its ordered list of preparation steps — is stored in a
dedicated table, `event_preparation_steps`, rather than a JSONB column on
`events`. This keeps the steps queryable (e.g., "what is the longest preparation
step across all events?") and avoids repeating the step names and durations
inside every event row.

| Column     | Type | Notes                                                           |
|------------|------|-----------------------------------------------------------------|
| `id`       | UUID | Primary key. A storage-only surrogate; never exposed by the API |
| `event_id` | UUID | FK → `events.id`, `ON DELETE CASCADE`                           |
| `name`     | text | 1–60 chars                                                      |
| `duration` | int  | Minutes, 1–1440                                                 |
| `position` | int  | Order in the sequence, 0-based                                  |

An index on `(event_id, position)` supports the natural read pattern of "get all
steps for this event in order":

```
ix_event_preparation_steps__event_id_position
```

`routine_start_at` is **not** a stored column. It is computed when an event is
returned, from `starts_at` and the sum of the steps' durations.

An override of a recurring event's routine for a single occurrence is stored on the
`recurrence_exceptions` row as a `jsonb` column (`routine_override`), since it is
only ever read together with that row.

### Recurrence Storage

`RecurrenceRule` is a value object, so it is flattened onto `events` and `tasks` as columns:

| Column                    | Type | Notes                                                                  |
|---------------------------|------|------------------------------------------------------------------------|
| `recurrence_frequency`    | text | `DAILY`, `WEEKLY`, `MONTHLY`, `YEARLY`; **null means "not recurring"** |
| `recurrence_interval`     | int  | ≥ 1, default 1                                                         |
| `recurrence_by_day`       | text | Comma-separated ISO day codes, e.g. `MO,WE,FR`. Weekly only            |
| `recurrence_by_month_day` | int  | Monthly only                                                           |
| `recurrence_end_type`     | text | `NEVER`, `UNTIL`, `AFTER_COUNT`                                        |
| `recurrence_until`        | date | If `UNTIL`; inclusive, in the row's `time_zone`                        |
| `recurrence_count`        | int  | If `AFTER_COUNT`                                                       |

The two value objects are deliberately stored differently: `RecurrenceRule` is a fixed, small set of scalar
fields that is read on every event, so columns are cheaper than a join; `PreparationStep` is a variable-length
list, so a child table is the natural shape. Neither choice is meant as a general rule.

### Calendar View Queries and Indexes

`GET /api/events?from=…&to=…` is the hottest read. It has to find, for one user:

1. non-recurring events that **overlap** the range, and
2. recurring events whose series could produce an occurrence in the range (started before the range ends, and not ended
   before it begins), which the server then expands.

Indexes:

| Index                                                                                                 | Serves                                 |
|-------------------------------------------------------------------------------------------------------|----------------------------------------|
| `ix_events__user_id_starts_at` on `(user_id, starts_at)`                                              | Range queries for non-recurring events |
| `ix_events__user_id_recurring` on `(user_id, starts_at)` **where `recurrence_frequency is not null`** | Finding series to expand; stays small  |
| `ix_tasks__user_id_scheduled_for` on `(user_id, scheduled_for)`                                       | My Day / This Week                     |
| `ix_tasks__user_id_due_at` on `(user_id, due_at)`                                                     | Due and Overdue                        |
| `ix_tasks__user_id_completed` on `(user_id, completed, completed_at)`                                 | Completed view and the streak          |

These are the starting set. Add or change indexes only after measuring against the real queries.

## Migrations

Migrations refer to the process of modifying a database schema in a controlled and organised way.
This typically involves creating, updating, or deleting tables, columns, or other database structures
to reflect changes in the application's data model. Migrations ensure that changes to the database schema
are versioned, and can be applied consistently across different environments (development, testing, production).

The migration tool chosen for this application is **Flyway**.
Flyway runs versioned SQL scripts and tracks which have already been applied
in a `flyway_schema_history` table.

**The server applies pending migrations automatically on startup, in every environment** — development, tests, and
production — before it begins serving requests. The Gradle tasks below exist for running migrations *without* starting
the server (for example, to inspect or prepare a database).

### Flyway Setup

Flyway runs inside the server at startup, using the Flyway library with the PostgreSQL module (`flyway-core` and, since
Flyway 10, `flyway-database-postgresql`).

For manual use, the same migrations are exposed through a **Gradle task** so that developers do not need to install a
separate CLI. The plugin is declared in the server module's build script:

```kotlin
plugins {
    id("org.flywaydb.flyway") version "<current 10.x release>"
}
```

Connection details are read from the `.env` file, so the same task works for any developer
without editing the build script.

Migration files are placed under:

```
planer-server/src/main/resources/db/migration/
```

### Create Migration

Migrations are plain `.sql` files, created by hand and added to the folder above.
There is no "generate migration" command — the schema is written explicitly,
which keeps the SQL readable and reviewable.

To create a new migration, create a file following the naming convention below and add your SQL. **Never edit a
migration that has been merged:** Flyway checksums every applied migration and refuses to start if one changed. Fix
mistakes with a new migration.

### Migration Naming Convention

Flyway requires the pattern:

```
V{version}__{description}.sql
```

- **version** — a monotonically increasing integer, starting at `1`
- **description** — a short, underscore-separated description of the change

Examples:

- `V1__create_users_table.sql`
- `V2__create_calendars_table.sql`
- `V3__create_events_table.sql`
- `V4__add_recurrence_rule_to_events.sql`
- `V5__add_is_default_to_calendars.sql`
- `V6__create_event_preparation_steps_table.sql`

**Version numbers are never reused.** If two developers create migrations at the same time,
the second one to merge must rename their file to the next available version.

### Apply Migration

To apply all pending migrations against the configured database without starting the server, run:

```sh
./gradlew :planer-server:flywayMigrate
```

This reads the connection details from the environment and applies every migration
that has not yet been recorded in `flyway_schema_history`.

To inspect the state of the schema without changing anything:

```sh
./gradlew :planer-server:flywayInfo
```

### Apply Migration — with the connection flag

If the target database is not the one configured in the environment, Flyway accepts connection
details as task parameters:

```sh
./gradlew :planer-server:flywayMigrate \
  -Pflyway.url=jdbc:postgresql://{{database_server}}:{{database_port}}/{{database_name}} \
  -Pflyway.user={{database_user}} \
  -Pflyway.password={{database_password}}
```

By default, for local development:

- **database_server** is `localhost`
- **database_port** is `5432`
- **database_name** is `planer`
- **database_user** is `planer`
- **database_password** is `planer`

Check the `.env` file if these have been changed.

Alternatively, the `apply-database-migrations.sh` shell script can be used,
which wraps the Gradle task with the values from `.env`.

### Rolling Back

The open-source edition of Flyway has **no undo migrations**; a migration cannot be rolled back with a command. PlaneR's
approach:

- **Roll forward.** If a migration was wrong, write a new migration that corrects it.
- **Make migrations safe to deploy.** Prefer additive changes (new nullable columns, new tables); split destructive
  changes (dropping a column) into a later migration, after no running version uses it.
- **Back up before a risky migration** in production (see [Deployment → Backups](Deployment.md#backups)).
- In development, `flywayClean` plus `flywayMigrate` rebuilds the database from scratch. `clean` is disabled by default
  and is enabled only in the development configuration.

## Connection Configuration

The server reads its database connection from environment variables,
which are loaded from the `.env` file at startup.

| Variable      | Purpose           | Default (dev) |
|---------------|-------------------|---------------|
| `DB_HOST`     | Database host     | `localhost`   |
| `DB_PORT`     | Database port     | `5432`        |
| `DB_NAME`     | Database name     | `planer`      |
| `DB_USER`     | Database user     | `planer`      |
| `DB_PASSWORD` | Database password | `planer`      |

For production, these are provided by the deployment environment and never committed.
See [Security](../security/Security.md) for how other secrets (JWT signing key, etc.) are handled.

## Data Access

The server uses **Exposed**, JetBrains' Kotlin-native SQL framework, with its **DSL** (not the DAO layer): table
definitions as Kotlin objects, type-safe queries that stay close to SQL, no annotations, no entity lifecycle to reason
about.

Exposed is used for queries only. **The schema is owned by the Flyway migrations.** Exposed table objects describe
tables that already exist; they are never used to create or alter them.

The following principles apply:

- **Migrations are the source of truth for the schema.** The Exposed table definitions are kept in step with the
  migrations by hand, and the integration tests (which run against a real migrated Postgres) catch any drift.
- **Parameterised statements are mandatory.** Exposed's DSL parameterises by construction; raw SQL strings built by
  concatenation are never allowed.
- **Ownership is enforced at the query level.** Every read and write is scoped by the authenticated user's `id`.

## Decisions and Open Questions

**Decided**

| Topic                    | Decision                                                                           |
|--------------------------|------------------------------------------------------------------------------------|
| Data access              | Exposed, DSL style                                                                 |
| UUID generation          | UUID v7, generated by the application                                              |
| Soft deletes             | None; hard deletes everywhere                                                      |
| Recurrence exceptions    | A dedicated `recurrence_exceptions` table, not JSONB on the parent                 |
| `RecurrenceRule` storage | Flattened columns; `by_day` as a comma-separated string                            |
| Calendar view indexes    | The set in [Calendar View Queries and Indexes](#calendar-view-queries-and-indexes) |

**Still open**

1. **Materialising `routine_start_at`.** It is computed on read today. If a query ever has to *filter or sort* events by
   it across many rows, a generated or stored column would be needed. The Summary endpoint only looks at upcoming
   events, so this is not expected to matter soon.
2. **Cleanup of expired tokens.** The daily job deletes expired and used `one_time_tokens` and expired or long-revoked
   `refresh_tokens`; the exact retention for revoked refresh tokens (they are kept a while so reuse detection still
   recognises them) is to be set when the job is written.
