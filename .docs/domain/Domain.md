## General

Every model has:

- a unique `id` (UUID v7, sortable by creation time, generated by the application)
- `createdAt` and `updatedAt` timestamps (Instant, UTC)

PlaneR is **single-user per account**. There is no sharing, no collaboration, no workspace or team concept. Every model
either *is* a User or belongs to one, and every read/write is scoped to the authenticated user.

### Colours and Icons

Where a model supports visual customization, two fields are used:

- **`color`** — a hex string (e.g., `#7C3AED`), rendered as the calendar's accent in the UI
- **`icon`** — a `CalendarIcon` enum value, mapped 1:1 to Material Icons on the client

Both are optional in the UI sense that the client falls back to a default if either is missing, but the API requires
them when creating a calendar.

## Models

### 👤 User

The account holder. Owns every other model in the system.

| Field           | Type    | Notes                                                            |
|-----------------|---------|------------------------------------------------------------------|
| `id`            | UUID    | Primary key                                                      |
| `email`         | string  | Unique, used for login, current confirmed address                |
| `emailVerified` | bool    | Whether the current email has been verified                      |
| `pendingEmail`  | string? | During an email change, the new address awaiting verification    |
| `passwordHash`  | string  | BCrypt                                                           |
| `displayName`   | string  | Shown in the UI                                                  |
| `avatarUrl`     | string? | Optional, an external `https` URL — PlaneR does not host avatars |
| `timezone`      | string  | IANA identifier (e.g., `Europe/Berlin`)                          |
| `createdAt`     | Instant |                                                                  |
| `updatedAt`     | Instant |                                                                  |

**Notes**

- Email is the identifier. No usernames.
- `timezone` matters because "today" and "this week" are computed in the user's local zone, not the server's. It is also
  the *default* `timeZone` for new events and tasks.
- A default Calendar ("Personal") is created automatically on registration.
- `emailVerified` starts as `false` on registration. An unverified account can use the application fully; the one
  restriction is that it cannot change its email. See [Security](../security/Security.md#email-verification).
- `pendingEmail` is only set during an email change. It is cleared either when the new address is verified (and `email`
  is updated to match, `emailVerified` reset to `true`) or when the change is cancelled or expires.
- Passwords are **never** stored in plain text — see [Security](../security/Security.md).

### 📅 Calendar

A **user-defined grouping** for events and tasks. This is the equivalent of Google Calendar's sidebar list — a coloured
category that items belong to. It is *not* the month grid; the month grid is computed in the UI from events across all
calendars.

| Field       | Type         | Notes                                             |
|-------------|--------------|---------------------------------------------------|
| `id`        | UUID         | Primary key                                       |
| `userId`    | UUID         | Owner (FK → User)                                 |
| `name`      | string       | e.g., "Work". Unique per user, case-insensitively |
| `color`     | string       | Hex, e.g., `#7C3AED`                              |
| `icon`      | CalendarIcon | Enum, see below                                   |
| `position`  | int          | Sidebar ordering                                  |
| `isDefault` | bool         | Exactly one per user                              |
| `createdAt` | Instant      |                                                   |
| `updatedAt` | Instant      |                                                   |

**Notes**

- "Responsibilities" is just a Calendar whose `name = "Responsibilities"`. No special entity.
- Events and Tasks *may* belong to a Calendar, but they do not have to. A null `calendarId` on those models means
  "unassigned".
- The default calendar cannot be deleted. Another calendar can be made the default, after which the old one becomes
  deletable.

**Suggested palette**

Only **Personal** is created automatically. The other entries are **presets** the client offers when the user adds a
calendar; choosing one just fills in the name, icon, and color.

| Name             | Icon        | Color     |
|------------------|-------------|-----------|
| Work             | `BRIEFCASE` | `#7C3AED` |
| Personal         | `STAR`      | `#F59E0B` |
| Health           | `HEALTH`    | `#10B981` |
| Family           | `FAMILY`    | `#EC4899` |
| Responsibilities | `FLAG`      | `#EF4444` |

### 🗓️ Event

A **time-bound occurrence** on the calendar. Something that happens at a specific time.

| Field            | Type                    | Notes                                                                                                          |
|------------------|-------------------------|----------------------------------------------------------------------------------------------------------------|
| `id`             | UUID                    | Primary key                                                                                                    |
| `userId`         | UUID                    | Owner (FK → User)                                                                                              |
| `calendarId`     | UUID?                   | Optional grouping (FK → Calendar)                                                                              |
| `title`          | string                  |                                                                                                                |
| `description`    | string?                 |                                                                                                                |
| `location`       | string?                 |                                                                                                                |
| `startsAt`       | Instant                 | Required                                                                                                       |
| `endsAt`         | Instant                 | Required                                                                                                       |
| `timeZone`       | string                  | IANA identifier. The zone in which recurrence and all-day boundaries are computed. See [Timezones](#timezones) |
| `allDay`         | bool                    | Renders as a banner instead of a block                                                                         |
| `recurrence`     | RecurrenceRule?         | See below                                                                                                      |
| `routine`        | List\<PreparationStep\> | Ordered; empty if none. See Preparation Steps below                                                            |
| `routineStartAt` | Instant?                | Derived from `startsAt` and the sum of the routine's durations. Not stored                                     |
| `createdAt`      | Instant                 |                                                                                                                |
| `updatedAt`      | Instant                 |                                                                                                                |

**Notes**

- Ownership is via `userId`. When `calendarId` is set, its `userId` must match.
- Events always have a time. When `allDay` is true, `startsAt` and `endsAt` are **local midnights in the event's
  `timeZone`**, and the UI renders it as a banner.
- An all-day event cannot have a routine.
- No `completed` flag — events happen, they are not "done".

### ✅ Task

A **to-do item**. Something the user needs to do and can mark as completed. May or may not have a scheduled time.

| Field              | Type            | Notes                                                                                                               |
|--------------------|-----------------|---------------------------------------------------------------------------------------------------------------------|
| `id`               | UUID            | Primary key                                                                                                         |
| `userId`           | UUID            | Owner (FK → User)                                                                                                   |
| `calendarId`       | UUID?           | Optional grouping (FK → Calendar)                                                                                   |
| `title`            | string          |                                                                                                                     |
| `description`      | string?         |                                                                                                                     |
| `dueAt`            | Instant?        | The deadline                                                                                                        |
| `scheduledFor`     | LocalDate?      | The day the user plans to do it, in the task's `timeZone`                                                           |
| `scheduledStartAt` | Instant?        | Optional time block on that day                                                                                     |
| `scheduledEndAt`   | Instant?        | Optional time block on that day                                                                                     |
| `timeZone`         | string          | IANA identifier. Defines the local date of a time block and how recurrence is expanded. See [Timezones](#timezones) |
| `completed`        | bool            |                                                                                                                     |
| `completedAt`      | Instant?        | Set on completion, cleared on uncompletion                                                                          |
| `position`         | int             | Ordering within one scheduled day; `0` when unscheduled                                                             |
| `recurrence`       | RecurrenceRule? | See below                                                                                                           |
| `createdAt`        | Instant         |                                                                                                                     |
| `updatedAt`        | Instant         |                                                                                                                     |

**Notes**

- Ownership is via `userId`. When `calendarId` is set, its `userId` must match.
- The scheduling fields serve different purposes:
    - `dueAt` — the **deadline** ("must be done by Friday")
    - `scheduledFor` — the **intent** ("I plan to do this Tuesday")
    - `scheduledStartAt` / `scheduledEndAt` — an optional **time block** on that day, rendered on the grid. It must fall
      on `scheduledFor` in `timeZone`.
- This is what powers the UI views:
    - **My Day** → `scheduledFor == today`
    - **This Week** → `scheduledFor` within the current week, or `dueAt` within the week
    - **Backlog** → `scheduledFor == null && dueAt == null`
    - **Completed** → `completed == true`
- A task can be completed without ever being scheduled.
- For a **recurring** task, `completed` / `completedAt` on the task itself are not used; completion is tracked per
  occurrence (see [Recurrence](#recurrence)).
- A Task can be **converted into an Event** when the user decides it has become a scheduled thing rather than a to-do.
  See "Task ↔ Event Conversion" below.

## Task vs Event — quick reference

|                 | Event                                        | Task                       |
|-----------------|----------------------------------------------|----------------------------|
| **Essence**     | Something that *happens*                     | Something you *need to do* |
| **Time**        | Always has start & end                       | Optional                   |
| **Completion**  | No completion state                          | Has `completed`            |
| **Preparation** | May carry a preparation routine              | Never carries one          |
| **Litmus test** | "Does it make sense to mark this done?" → No | → Yes                      |
| **Example**     | "Team Standup, 9:00–9:30"                    | "Buy groceries"            |
| **Example**     | "Doctor Appointment, 8:00–9:00"              | "Call dentist"             |
| **Example**     | "Family Brunch, 10:00–12:00"                 | "Fix leaky faucet"         |
| **UI location** | Grid block                                   | Checklist item             |

## Timezones

All instants are stored and transmitted in **UTC**. A UTC instant alone cannot express "every day at 09:00 local time",
though — across a daylight-saving change, 09:00 in Berlin is 08:00 UTC in summer and 07:00 UTC in winter. So events and
tasks also carry a **`timeZone`**.

- **Recurrence is expanded in the item's `timeZone`.** A weekly 09:00 standup created in `Europe/Berlin` stays at 09:00
  Berlin time all year; the server computes the correct UTC instant for each occurrence.
- **All-day boundaries are local midnights in the item's `timeZone`.** An all-day event on 15 July in `Europe/Berlin`
  starts at `2025-07-14T22:00:00Z`.
- **`User.timezone` is a default and a lens, not an anchor.** It supplies the `timeZone` for newly created items, and it
  defines "today" and "this week" for the views and for date-range filters.
- **Changing `User.timezone` does not move existing items.** A meeting scheduled at 09:00 Berlin time is still at that
  instant after the user moves to London; the client now *displays* it in London time. Only items created afterwards
  default to the new zone.
- **Routines are unaffected.** Preparation steps are durations in minutes; the timeline is plain arithmetic backward
  from `startsAt`, with no timezone involved. (The rendered times are shown in the user's zone by the client.)

## Task ↔ Event Conversion

A Task and an Event represent different intents, but a user's intent can change over time.
A task that has been given a fixed time slot may effectively *become* an event, and vice versa.

PlaneR models this as an explicit **conversion** rather than a link:

- **Task → Event** — the Task is deleted and a new Event is created from its fields, in one transaction.
  The Task's `scheduledStartAt` / `scheduledEndAt` become the Event's `startsAt` / `endsAt`, unless overridden in the
  request. If neither is available the request fails; an event must have a time. The new Event starts with an empty
  `routine`.
- **Event → Task** — the Event is deleted and a new Task is created from its fields, in one transaction.
  The Event's `routine` is **discarded** — a Task has no preparation concept.

In both directions:

- the result gets a **new id**, and the old id stops existing
- `createdAt` is preserved
- `title`, `description`, `calendarId`, `timeZone`, and `recurrence` carry over
- fields with no counterpart are dropped (`location`, `dueAt`, `position`, completion state)
- for recurring items, only the series converts; occurrence overrides, skips, and completions are dropped

**Why not link them?** A "task that has become an event" is a conceptual change, not a relationship. Keeping both around
would double the surface area of every query and give the UI no clean way to represent a task that is now an event.

This is exposed as two endpoints:

- `POST /api/tasks/{id}/convert-to-event` — documented in [Api.Task](../api/controllers/Api.Task.md#convert-to-event)
- `POST /api/events/{id}/convert-to-task` — documented in [Api.Event](../api/controllers/Api.Event.md#convert-to-task)

## Recurrence

Recurrence is modelled as a **`RecurrenceRule`** value object, shared by Event and Task.
It loosely follows RFC 5545 (iCalendar) but only includes the fields a personal planner actually needs.

### 🔁 RecurrenceRule *(value object)*

| Field        | Type              | Notes                               |
|--------------|-------------------|-------------------------------------|
| `frequency`  | Frequency         | Daily / Weekly / Monthly / Yearly   |
| `interval`   | int               | Every N (default 1)                 |
| `byDay`      | Set\<DayOfWeek\>? | For Weekly only (e.g., Mon/Wed/Fri) |
| `byMonthDay` | int?              | For Monthly only (e.g., 15)         |
| `end`        | RecurrenceEnd     | When the series stops               |

If `byMonthDay` is greater than the length of a given month (for example `31` in April), the occurrence falls on that
month's **last day**. A yearly rule on 29 February falls on 28 February in non-leap years.

### 🛑 RecurrenceEnd *(value object)*

| Field       | Type                       | Notes                                                         |
|-------------|----------------------------|---------------------------------------------------------------|
| `type`      | Never / Until / AfterCount |                                                               |
| `untilDate` | LocalDate?                 | If Until. **Inclusive**, interpreted in the item's `timeZone` |
| `count`     | int?                       | If AfterCount                                                 |

**How occurrences are produced**

- **Events** — stored once with the rule; the server expands the rule into concrete occurrences when the client requests
  a date range. One row in the database, many occurrences in the response.
- **Tasks** — the same expansion, but completion is **per occurrence**. Each occurrence that gets completed creates a
  `TaskCompletion` record (see [Supporting Records](#supporting-records)). The UI then marks that specific occurrence as
  done.

**Exceptions and overrides**

- If the user edits a single occurrence (e.g., moves the July 20 standup to 10am), a **`RecurrenceException`** record is
  stored that says *"for entity X, on date Y, apply these overrides."* This is the standard iCalendar approach and keeps
  the recurring entity intact.
- If the user skips an occurrence, a `RecurrenceException` is stored with `skipped = true`.
- If the user changes "this and all following" occurrences, the series is **split**: the original series is ended the
  day before, and a new series carrying the changes begins on that date. Exceptions dated on or after the split move
  with the new series.

**Presets for the UI** (so the user doesn't type RRULEs)

| Label                   | Rule                                       |
|-------------------------|--------------------------------------------|
| Every day               | `{ FREQ=DAILY, interval=1 }`               |
| Every weekday           | `{ FREQ=WEEKLY, byDay=[Mon..Fri] }`        |
| Every week on Tuesday   | `{ FREQ=WEEKLY, byDay=[Tue] }`             |
| Every 2 weeks on Monday | `{ FREQ=WEEKLY, interval=2, byDay=[Mon] }` |
| Every month on the 15th | `{ FREQ=MONTHLY, byMonthDay=15 }`          |
| Every year              | `{ FREQ=YEARLY }`                          |
| Custom…                 | opens the full editor                      |

**Storage**

`RecurrenceRule` is a value object, so it flattens onto the parent table as columns (`recurrence_frequency`,
`recurrence_interval`, `recurrence_by_day`, `recurrence_by_month_day`, `recurrence_end_type`, `recurrence_until`,
`recurrence_count`).
`byDay` is stored as a comma-separated string of ISO day codes (`MO,WE,FR`).
See [Database](../infrastructure/Database.md).

## Preparation Steps

A **preparation step** is an ordered step the user performs *before* an event starts.
It is used for **reverse planning**: the event has a fixed `startsAt`, and the
preparation steps are laid out backward from it, so the user knows when to start
getting ready.

Example: an event at 17:30 with a routine of "Shower (40 min)", "Dress (30 min)",
"Walk dog (20 min)", "Travel (30 min)" yields a `routineStartAt` of 15:30.

### 🧭 PreparationStep *(value object)*

Attached to an Event as its `routine`. The list is ordered.

| Field      | Type   | Notes                               |
|------------|--------|-------------------------------------|
| `name`     | string | "Shower", "Walk dog", "Travel"      |
| `duration` | int    | How long the step takes, in minutes |
| `position` | int    | Order in the sequence               |

A `PreparationStep` has no ID and no timestamps in the domain. It lives and dies with its event. (The database gives
each row a surrogate key purely for storage; the API never exposes it.)

**Notes**

- Preparation steps are **strictly sequential**. No overlap. If the user needs a gap, they add a step called "Wait" with
  the appropriate duration.
- They are **not** tasks. A preparation step cannot be completed, has no calendar, and is never queried on its own.
- They are **not** events. A preparation step is a *duration*, not a moment.
- Only events with `allDay = false` can have a routine.
- Limits: at most 20 steps, each 1–1440 minutes, with a total of at most 1440 minutes.
- On a recurring event the routine belongs to the series; an occurrence override may replace it for that occurrence.

### Event additions

The Event model gains two fields:

| Field            | Type                    | Notes                                       |
|------------------|-------------------------|---------------------------------------------|
| `routine`        | List\<PreparationStep\> | Ordered; empty if none                      |
| `routineStartAt` | Instant?                | Derived: `startsAt - sum(routine.duration)` |

`routineStartAt` is a **derived field**. The source of truth is the steps and
the event start time; the server computes it whenever it returns an event. It is **not stored**. "What do I need to
start preparing for soon?" is answered by the
[Summary](../api/controllers/Api.Summary.md) endpoint, which looks only at upcoming
events, so it does not need an index on a derived value.

### Computed timeline

When the server returns an event with a routine, it also returns the computed
`startsAt` and `endsAt` for each step, so the client doesn't have to do the
arithmetic:

| Step      | Starts    | Ends      |
|-----------|-----------|-----------|
| Shower    | 15:30     | 16:10     |
| Dress     | 16:10     | 16:40     |
| Walk dog  | 16:40     | 17:00     |
| Travel    | 17:00     | 17:30     |
| **Event** | **17:30** | **18:00** |

Timestamps are sent as UTC; the client renders them in the user's local zone.

**Routines (deferred)**

A reusable template of preparation steps — a `Routine` model that can be applied
to an event — is planned for a future version. In v1, the steps live directly on
the event. Applying a routine in the future will **copy** the steps onto the
event rather than linking, so editing a routine never changes events that
already used it.

## Supporting Records

These are not user-facing concepts, but the rest of the documentation refers to them. They are stored in the database;
see [Database](../infrastructure/Database.md).

### TaskCompletion

Records that one occurrence of a **recurring** task was completed.

| Field            | Type      | Notes                       |
|------------------|-----------|-----------------------------|
| `taskId`         | UUID      | FK → Task                   |
| `occurrenceDate` | LocalDate | The occurrence's local date |
| `completedAt`    | Instant   |                             |

Unique on `(taskId, occurrenceDate)`.

### RecurrenceException

An override or a skip for one occurrence of a recurring event or task.

| Field                | Type      | Notes                                                                                                                                                                                                                  |
|----------------------|-----------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `id`                 | UUID      | Primary key                                                                                                                                                                                                            |
| `eventId` / `taskId` | UUID      | Exactly one is set (FK → Event or Task)                                                                                                                                                                                |
| `occurrenceDate`     | LocalDate | The occurrence this applies to                                                                                                                                                                                         |
| `skipped`            | bool      | If `true`, the occurrence does not appear                                                                                                                                                                              |
| overridden fields    |           | `title`, `description`, `location`, `startsAt`, `endsAt`, `allDay`, `routine` for events; `title`, `description`, `dueAt`, `scheduledFor`, `scheduledStartAt`, `scheduledEndAt` for tasks. Null means "not overridden" |

Unique per `(eventId or taskId, occurrenceDate)`.

### RefreshToken

One issued refresh token. Stores only the **hash** of the token, the user, a `familyId`, expiry, and revocation state.
See [Security](../security/Security.md#refresh-tokens).

### OneTimeToken

A single-use token for email verification or password reset. Stores only the **hash**, the user, the purpose, the email
concerned, the expiry, and when it was used. See [Security](../security/Security.md#one-time-tokens).

## Enums

### 🎨 CalendarIcon

`BRIEFCASE`, `HOME`, `STAR`, `FLAG`, `BOOK`, `MUSIC`, `FITNESS`, `FOOD`, `TRAVEL`, `MONEY`, `EDUCATION`, `FAMILY`,
`HEALTH`, `DEFAULT`

Each value stands for a distinct concept; there are deliberately no near-duplicates (such as a separate `WORK` next to
`BRIEFCASE`).

Mapped 1:1 to Material Icons on the client.
The API validates incoming `icon` values against this enum.

**Why an enum, not a free string?**

- Free strings lead to inconsistency ("briefcase", "Briefcase", "work-icon" for the same concept).
- Emoji render differently across platforms (Windows, macOS, Android), which breaks visual consistency in the sidebar.
- An enum maps cleanly to a shared icon set across the **Compose for Desktop** and **Jetpack Compose** clients.

If the user wants a custom look, they can change the **color** instead — that field stays free-form.

### 🔁 Frequency

`DAILY`, `WEEKLY`, `MONTHLY`, `YEARLY`

### 🛑 RecurrenceEndType

`NEVER`, `UNTIL`, `AFTER_COUNT`

## Derived Concepts

Not stored as their own models — computed from the ones above. The server computes them in the user's timezone and
serves them through [Api.Summary](../api/controllers/Api.Summary.md) (or, for per-calendar
counts, [Api.Calendar](../api/controllers/Api.Calendar.md)).

| Concept              | Source                                                                    | Purpose                                      |
|----------------------|---------------------------------------------------------------------------|----------------------------------------------|
| **Streak**           | `Task.completedAt` and `TaskCompletion.completedAt`, grouped by local day | Powers the "6 days 🔥" card                  |
| **Focus Now**        | Next upcoming event or scheduled task                                     | Powers the "Focus Now" panel                 |
| **Routine Start**    | `Event.startsAt - sum(routine.duration)`                                  | Powers the "start preparing at 3:30 PM" card |
| **Overdue**          | `Task.dueAt < now && !completed`                                          | Powers the Overdue card                      |
| **Today's Progress** | Tasks scheduled for today, completed vs. total                            | Powers the "3 / 7" progress                  |
| **Calendar counts**  | Events + tasks per calendar for the sidebar                               | Powers the "8", "5", "3" badges              |

## Deferred

The following are intentionally left out of the initial domain and will be added if needed:

- **Routines** — reusable templates of preparation steps (see Preparation Steps above)
- **Reminders / notifications** — would require a `Reminder` model and a scheduler. A narrow, client-only "start
  preparing" notification for a routine is planned separately; see [Features](../features/Features.md)
- **Attachments** — would require a storage layer
- **DailyCheckIn** — the "Energy Level Today" feature; to be decided
- **Sharing / collaboration** — PlaneR is single-user for now
